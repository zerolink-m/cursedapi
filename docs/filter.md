# Продвинутый фильтр (`filter`) — cursedapi v1.2

`filter` — необязательный query-параметр для выборки по составным условиям. Он не является SQL: сервер никогда не вставляет его текст в запрос к БД. Для простого поиска остаются `search`, `search_column` и `search_method` (см. [query.md](query.md)).

## Передача

Клиент составляет UTF-8 строку выражения, кодирует её в **Base64url без завершающих `=`** (RFC 4648 §5) и передаёт как значение `filter`. При построении URL применяются обычные правила URL-кодирования параметров; сервер сначала разбирает query-строку и выполняет её percent-decoding **ровно один раз**, затем декодирует Base64url и UTF-8, после чего разбирает выражение. Дополнительной замены «опасных символов» нет: Base64url уже использует безопасный для URL алфавит. Кодирование не обеспечивает безопасность или секретность.

Исходное выражение:

```text
(status IN ['active', 'pending'] AND age >= 18) AND NOT (email IS NULL OR name STARTS_WITH 'test')
```

Его представление в URL:

```text
GET /v1/users?filter=KHN0YXR1cyBJTiBbJ2FjdGl2ZScsICdwZW5kaW5nJ10gQU5EIGFnZSA-PSAxOCkgQU5EIE5PVCAoZW1haWwgSVMgTlVMTCBPUiBuYW1lIFNUQVJUU19XSVRIICd0ZXN0Jyk
```

## Язык выражений

Грамматика (ключевые слова не чувствительны к регистру; имена полей чувствительны, если схема ресурса не оговаривает иное):

```text
expression := or_expr
or_expr   := and_expr (OR and_expr)*
and_expr  := not_expr (AND not_expr)*
not_expr  := NOT not_expr | '(' expression ')' | predicate
predicate := field comparison literal
           | field (NOT)? IN '[' literal (',' literal)* ']'
           | field (NOT)? BETWEEN literal AND literal
           | field IS (NOT)? NULL
           | field string_op string
comparison := '==' | '!=' | '<' | '<=' | '>' | '>='
string_op  := CONTAINS | STARTS_WITH | ENDS_WITH
field      := имя поля из разрешённой схемы ресурса
literal    := строка | число | true | false
```

Приоритет: скобки, `NOT`, `AND`, `OR`; операторы одного уровня вычисляются слева направо. `BETWEEN a AND b` включает обе границы и трактует свой `AND` как часть оператора. `NOT IN`, `NOT BETWEEN` и `IS NOT NULL` — единые операторы. Строковые операции ищут **буквальную подстроку**: `%` и `_` не являются шаблонами. Сравнение строк чувствительно к регистру; другая семантика может быть объявлена как отдельная возможность сервера, но не должна молча менять эти правила.

Строки заключаются в одинарные кавычки; внутри допускаются только `\\` и `\'`. Числа записываются десятичными цифрами с необязательным `-` и дробной частью через точку. Типы полей определяет схема ресурса: сервер отвергает сравнения несовместимых типов; операции порядка — только для упорядочиваемых типов, строковые — только для строк. `== null` и `!= null` не допускаются: для null служит `IS [NOT] NULL`; `null` в `IN` или `BETWEEN` тоже не допускается. Предикат над null-полем (кроме `IS [NOT] NULL`) даёт `false`, а логические операции работают с обычными булевыми значениями, без SQL-трёхзначной логики. Даты и время передаются строками в формате, объявленном схемой поля. Неизвестные идентификаторы, вызовы функций, арифметика, обращения к таблицам, подзапросы и произвольные команды не входят в грамматику; слова вроде `SELECT` допустимы только **внутри строкового литерала**.

В v1.2 фильтровать можно только по разрешённым полям текущего ресурса (без `object.` и без перехода к связанным объектам). Сервис публикует разрешённые поля, типы, операторы и собственные лимиты в своей схеме эндпоинта; общая спецификация не предполагает, что все поля ответа доступны для фильтрации.

## Поведение и ограничения

- `filter` применяется **до** вычисления `settings.total`, `limit` и `offset`; сортировка задаётся обычными `sort_by`/`order`.
- При одновременной передаче `filter` и простого `search` условия соединяются через `AND`. Ограничения доступа сервера применяются независимо от обоих фильтров и не могут быть отменены выражением клиента.
- В запросе допускается ровно одно значение `filter`; пустое или повторённое значение — ошибка `118`. Сервер ограничивает длину URL и декодированного выражения, глубину скобок, число условий и размер списка `IN`; превышение опубликованного лимита — `118` с деталями в `error.query.filter` (слишком длинный URL может быть отклонён с HTTP 414, код `106`).
- Некорректный Base64url, UTF-8, синтаксис, неизвестное или недоступное поле, несовместимый оператор/тип — код `118` (HTTP 400) с `error.query.filter`. Сообщение может содержать позицию ошибки, но не обязано повторять исходный фильтр и не раскрывает внутреннюю схему БД.
- Реализация разбирает выражение в ограниченное дерево, проверяет поле и оператор по схеме **для данного клиента**, применяет ограничения на сложность и строит параметризованный запрос. Запрет слов или символов и одно лишь прохождение синтаксического разбора не являются защитой.

## Обнаружение поддержки

По умолчанию функция выключена. `OPTIONS` сообщает `GET.filter` (или `METHOD.filter` для другого метода) в `cursed-supported-functions`, только если функция включена для этого метода; необязательный `cursed-filter` может дополнительно сообщить `on` или `off`. Если функция не реализована — `181`, если реализована, но отключена — `182`. При включённом фильтре `OPTIONS` обязательно указывает `cursed-schema-url` (см. [headers.md](headers.md)). URL доступен через GET с обычной авторизацией и возвращает CursedJSON. Для каждого метода, где фильтр включён, его разрешённые поля и лимиты находятся в `data.schema.methods.METHOD.query.filter` (см. [schema.md](schema.md)):

```json
{
    "code": "000",
    "code_detail": "Success.",
    "error": {},
    "metadata": {},
    "data": {
        "schema": {
            "path_template": "/v1/users",
            "path_parameters": {},
            "methods": {
                "GET": {
                    "query": {
                        "filter": {
                            "encoding": "base64url",
                            "fields": {
                                "age": { "type": "int", "operators": [">=", "<=", "==", "BETWEEN", "IN"] },
                                "status": { "type": "string", "operators": ["==", "IN"] }
                            },
                            "limits": { "max_expression_bytes": 2048, "max_depth": 8, "max_conditions": 20, "max_in_items": 50 }
                        }
                    },
                    "responses": { "200": [ { "code": "000", "content_type": "application/json", "body_schema": {} } ] }
                }
            }
        }
    }
}
```

`body_schema: {}` в примере — сокращение; опубликованная схема ответа должна быть полной (см. [schema.md](schema.md)). Ключи `fields` — имена полей в выражении. `operators` перечисляет применимые к ним операции из грамматики; `NOT` и `AND`/`OR` — общие логические операции, а не операторы полей. В `limits` все четыре показанных положительных целых числа обязательны, значения выбирает сервер. Ответ должен учитывать права клиента и не раскрывать недоступные поля; если он зависит от авторизации, сервер не должен разрешать общему кешу хранить или отдавать его другим клиентам. Адрес может также предоставлять схему тела запроса для этого эндпоинта; формат таких дополнительных данных определяется сервисом.
